## Understanding
- Outcome: the repository publishes canary snapshots of the 8 `@websublime/line-*` packages from `main` on
  demand, and opens the Changesets Version PR whose merge publishes the stable versions. Publishing
  authenticates through npm trusted publishing (OIDC).
- Stated (spec §6.F.5): `release.yml` runs on push to `main` with `changesets/action@v1` and
  `publish: bun run release`; `snapshot-version.yml` and `snapshot-deploy.yml` wire `snapshot:version` and
  `snapshot:publish` into manual-dispatch and/or push-to-`main` flows; there is no `next` branch (AM-008);
  the snapshot workflows write the npm auth line themselves.
- Stated (spec §9.5 / §9.6): `@websublime/*` scope verified by at least one snapshot/canary publish; at least
  one RC publish verified end-to-end.
- Assumed: the end-to-end publish happens after the merge, because a `workflow_dispatch` workflow can only be
  dispatched once its file exists on the default branch.

## Evidence (Bun 1.3.14, `@changesets/cli` 2.31.0, probes in a throwaway worktree of `a049305`)
- `bun run version` (`changeset version`) bumps `line-colors`, `line-core`, `line-icons`, `line-schemas`,
  `line-tokens`, `line-utils` to `0.1.0` and `line-themes`, `line-components` to `0.0.1`. Afterwards
  `bun install --frozen-lockfile` exits 0 and `bun.lock` is unchanged, so the Version PR and `release.yml`
  do not break on the lockfile.
- `bun run snapshot:version` with neither `GITHUB_TOKEN` nor `GH_TOKEN` set fails inside
  `@changesets/changelog-github` (GitHub API). With a token it writes `<version>-<40-char sha>-SNAPSHOT`
  (`snapshot.prereleaseTemplate` = `{commit}-SNAPSHOT`).
- After `bun run build`, `bun run snapshot:publish --dry-run` plans 8 × `publish`, `tag=canary`, order
  colors, core, schemas, themes, tokens, icons, utils, components.
- `npm view @websublime/line-<name>` returns E404 for all 8: nothing has been published.
- GitHub: secrets `NPM_TOKEN` (created 2021-04-01) and `GH_TOKEN` (2023-06-28); default workflow permissions
  `write`, `can_approve_pull_request_reviews: true`; `main` protection requires no status checks and no
  reviews.
- npm (https://docs.npmjs.com/about-access-tokens, https://docs.npmjs.com/trusted-publishers):
  - Classic tokens were revoked on 2025-12-09. A secret created in 2021 predates granular tokens, so
    `NPM_TOKEN` is assumed dead (the value cannot be read).
  - Granular tokens are limited to 90 days, and publishing new versions directly with a granular token is
    removed in January 2027.
  - Trusted publishing needs npm CLI ≥ 11.5.1 and Node ≥ 22.14, `id-token: write`, and a `repository.url`
    in the published `package.json` that matches the GitHub repository. It is configured per package in the
    package settings on npmjs.com, one connection per workflow filename, so the package must exist first.
    Connections created after 2026-09-03 allow only `npm stage publish` by default; `npm publish` must be
    ticked. A `workflow_dispatch` run is validated against the calling workflow's filename. Provenance is
    generated automatically for public packages published from a public repository.
- None of the 8 package manifests declares `repository`. The private root declares
  `ssh://git@github.com:websublime/line-ui.git`.
- `.github/actions/npmrc/action.yml` writes `@websublime:registry=https://npm.pkg.github.com` into
  `~/.npmrc` (against PRD §6.4 "npm public"). No workflow uses it, and spec §5 lists no `.github/actions/`.
  Handed on by `00-F9`.
- `00-F9` handoff: keep `changesets/action@v1`; its `main` branch reads a `CHANGESETS_OUTPUT` file that CLI
  2.31.0 never writes.

## Acceptance criteria (agreed with Miguel)
1. PRD revision-log entry v0.8.4 ratifies AM-008, with the plan aligned in the same commit. A grep for the
   `next`-branch RC framing returns zero live hits (PROCESS §3).
2. `release.yml` runs on push to `main`. `changesets/action@v1` opens or updates the Version PR while
   changesets are pending, and runs `bun run release` when none are.
3. `snapshot-version.yml` (manual dispatch): computes the snapshot versions and prints the
   `snapshot:publish --dry-run` plan. No upload, commit, tag, or npm credential.
4. `snapshot-deploy.yml` (manual dispatch, `main` only): versions and publishes the snapshot in one job under
   the `canary` dist-tag. No commit, tag, or push. A run never uploads a version without the snapshot suffix.
5. The publishing workflows (`release.yml`, `snapshot-deploy.yml`) grant `id-token: write` and run npm CLI
   ≥ 11.5.1 on Node ≥ 22.14. `NPM_TOKEN` is optional: when the secret is set, npm can fall back to it; when it
   is unset, npm relies on OIDC and no auth line carries an empty token.
6. Each of the 8 published packages declares `repository` for `github.com/websublime/line-ui` with its
   `directory`; `scripts/verify-pack.mjs` reports 0 failures.
7. `.github/actions/npmrc/` is removed.
8. Verify record: `bun run lint`, `bun run build`, `actionlint` on every workflow, `scripts/verify-pack.mjs`,
   `bun run release --dry-run`, a snapshot version + `snapshot:publish --dry-run` in a scratch copy; changeset
   `patch` for the 8 packages.
9. After the merge (spec §9.5 / §9.6, outside this PR): a first canary of all 8 through `snapshot-deploy.yml`
   with a fresh granular `NPM_TOKEN`; Miguel configures trusted publishing on each package for
   `release.yml` and `snapshot-deploy.yml` with `npm publish` allowed; a later canary from a new `main`
   commit publishes through OIDC with `NPM_TOKEN` removed.

## Decisions (Miguel, 2026-10-06)
- **F-1 — ratify AM-008 in the PRD (v0.8.4).** No `next` branch. RCs are canary snapshots published from
  `main`. A stable release is the merge of the Changesets Version PR on `main`; during Phase 00 that PR stays
  unmerged, and merging it at Phase 00 exit ships `0.1.0`. The plan is aligned in the same commit. Rejected:
  restoring `next`, which reverts AM-008 and the B5 config.
- **F-2 — npm trusted publishing (OIDC), bootstrapped by a token.** A short-lived granular `NPM_TOKEN` publishes
  the first canary, because trusted publishing is configured on packages that already exist. Miguel then
  configures a trusted publisher for `release.yml` and `snapshot-deploy.yml` on each package, and the token is
  removed. The publishing workflows run npm ≥ 11.5.1; the packages declare `repository`; provenance comes
  with trusted publishing. Rejected: granular token only (90-day rotation, direct publishing removed
  January 2027); staged publishing (each version needs a maintainer 2FA approval, heavy for canaries).
- **F-3 — two manual-dispatch snapshot workflows.** `snapshot-version.yml` is a dry run that prints the
  snapshot plan. `snapshot-deploy.yml` versions and publishes in the same job, ephemeral. Rejected: a canary
  on every push to `main`; the legacy two-step flow (a PR into a `changeset-snapshot/**` branch whose merge
  triggers a `pull_request_target` publish), which commits snapshot versions and widens the attack surface.
- **Orchestrator defaults.** `snapshot-deploy.yml` publishes only from `main` (spec §7.2).
  `.github/actions/npmrc/` is removed as obsolete (`00-F9` handoff, spec §5).
- **Review gate, iteration 1 (2026-10-06; reviewer PASS, infra lens PASS, findings applied before the code).**
  - Both publishing jobs run in the GitHub Environment `npm`, whose deployment branch policy allows only
    `main`. A workflow file on another ref cannot publish: the trusted-publisher connections name the
    environment, and the bootstrap `NPM_TOKEN` is an environment secret. Without it, a branch copy of
    `snapshot-deploy.yml` or `release.yml` would satisfy a connection that matches only the workflow
    filename.
  - `snapshot-deploy.yml` fails, rather than skips, when dispatched from a ref other than `main`.
  - Since 2026-06-11, a PR opened by `github-actions[bot]` runs workflows once a user with write access
    approves them. Before merging the Version PR, Miguel approves its pending `checks.yml` run (or closes
    and reopens the PR).
  - The new workflows use the `actions/checkout` major that runs on Node 24; Node 20 left the runners on
    2026-09-23.
