## Understanding
- Outcome: `@websublime/line-icons` exports an agnostic `IconRegistry`, the `IconResolver` type, a shared
  `iconRegistry` singleton, and two reference resolver factories that prove the contract against two
  differently shaped libraries.
- Stated (spec §6.E.1): `IconResolver = (name, options?) => Promise<string | SVGElement>`; opaque
  `IconResolverOptions` bag; `IconRegistry` with `register`, `has`, `resolve`; `resolve` throws
  `[line-icons] No resolver registered for library "<library>".` for an unknown library.
- Stated (spec §6.E.2): `createLucideResolver()` imports `lucide-static/icons/<name>.svg?raw`;
  `createPhosphorResolver({ weight? })` takes the weight from `options.weight`, then the factory default,
  then `'regular'`. Both use `/* @vite-ignore */` dynamic imports.
- Stated (spec §4.8): one export (`.`); subpaths (`./registry`, `./resolvers/*`) wait for Phase 1.
- Stated (code): `packages/line-icons/src/index.ts` is `export {};`; build is `tsc -b`; the package depends
  on `@websublime/line-tokens` only; `lucide-static@1.16.0` and `@phosphor-icons/core@2.1.1` are root
  `devDependencies`.
- Assumed: an unknown icon name rejects with the module-resolution error of the dynamic import (spec silent).

## Spec drift found
- **Phosphor file names carry the weight suffix.** `@phosphor-icons/core@2.1.1` names every non-regular file
  `<name>-<weight>.svg` (`assets/bold/acorn-bold.svg`); only `regular` uses the bare name. The spec path
  `assets/${weight}/${name}.svg` fails for 5 of 6 weights. Probe (throwaway `bun test`, Bun 1.3.14):
  `assets/bold/acorn.svg?raw` → `Cannot find module`; `assets/<w>/acorn[-<w>].svg?raw` resolves for all six
  weights. Factual correction to §6.E.2 → `AM-033`.
- **No drift on `?raw`.** Bun 1.3.14 resolves `*.svg?raw` to the file text natively under `bun test`, so the
  resolvers need no preload plugin (unlike `?inline`, AM-026).

## Risks
- `/* @vite-ignore */` leaves a bare specifier with a Vite-only `?raw` query in the emitted JS. A browser app
  that calls a reference resolver through Vite most likely fails to resolve it [INFERENCE, not probed]. The
  Phase 00 acceptance is Bun-only, so E1 follows the spec and the PR body hands the risk to the Phase 1
  `<line-icon>` spec.

## Decisions (Miguel, 2026-10-02)
- **Icon libraries are optional peer dependencies.** `packages/line-icons/package.json` declares
  `lucide-static` `^1.16.0` and `@phosphor-icons/core` `^2.1.1` under `peerDependencies`, each marked
  `optional: true` in `peerDependenciesMeta`. The root `devDependencies` keep both for the tests. A consumer
  installs only the library whose resolver it uses. Rejected: hard `dependencies` (every consumer installs
  ~96 MB of icons, against ARCHITECTURE §11 "the consumer brings their own resolver"); undeclared imports
  (strict package managers refuse them, and the consumer gets no version range).
- **The §6.E.3 tests land in the E1 PR, and `00-E3` closes with it.** The Phosphor fix ships with its
  regression test and the Verify record runs real package tests. Precedent: `00-C10` and `00-C11` shared #189.
- Both land as `AM-033` (trigger `decision`) in a `docs(spec)` commit before the code. AM-033 carries the
  factual Phosphor path correction to §6.E.2 and the peer-dependency addition to the §4.8 `package.json`
  block.
