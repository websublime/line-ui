## Understanding
- Outcome: every `--line-shadow-*` token draws a soft shadow that matches the Open Props reference in light and
  dark, takes its tint from the nearest gray role, and works with `line-colors` alone.
- Evidence (Chromium, `shadow-4`, `src/` CSS):

  | Variant | Light | Dark |
  |---|---|---|
  | Today (`--line-gray-a-12`) | `box-shadow: none` | `none` |
  | Rename to `--line-gray-a12` | `rgba(0, 5, 9, 0.89)` on all 6 layers, a thick black rim | `rgba(252, 253, 255, 0.937)`, a white glow |
  | Open Props 1.7.23 geometry and opacity | 3–7 % per layer | 27–31 % per layer |
  | Prototype, `light-dark()` over `color-mix()` | first layer alpha 0.03 | first layer alpha 0.27 in a dark container on a light page |

- Evidence on scoping (Chromium, `<html data-gray="slate">`): a nested `data-gray="sand"` scope kept the slate
  colour, and `--line-shadow-color: red` set on an element did not reach `var(--line-shadow-4)` there. A
  custom property's `var()` is substituted on the element that declares it (the AM-049 mechanism).
- Stated (Miguel):
  - Fix colour, opacity and dark mode in this row.
  - Take the colour from `--line-gray-*` with a `--line-neutral-*` fallback and declare it in every theming scope.
  - Switch dark mode with `light-dark()` only, so the shadows do not depend on row `Z14`.
- Stated (spec §6.C.2): `:where(html)`, `--line-*` names, Open Props as a design reference, no runtime dependency.
- Assumed (orchestrator defaults, Miguel may correct):
  - The selector is `:where(html, [data-accent], [data-gray])`, as AM-049 set for the aliases, because
    `defaults.css` auto-pairs the gray role inside any `[data-accent]` scope without `data-gray`.
  - Light uses gray step 12 and dark uses gray step 1, both opaque; `color-mix()` with `transparent` supplies the
    opacity. Without `line-themes` the same steps come from `--line-neutral-*`.
  - `--line-shadow-strength` keeps its name and its 1 % default and drives light mode. A new
    `--line-shadow-strength-dark` (25 %) drives dark mode. Both match Open Props.
  - Each layer takes Open Props' opacity offset (+2 to +9 points) through one colour token per offset, the way
    Open Props uses `--shadow-strength-{3..8,10}`. The AM fixes the names.
  - The inner shadows use the +9 offset, as Open Props does. They get no highlight layer, because Open Props
    builds it from colour literals.
  - An override of a shadow knob on `<html>` must reach every nested theming scope. The knobs are not declared
    again in those scopes. One way to do this is to declare the strength knobs in `:where(html)` only, and
    to read `--line-shadow-color` as an optional consumer knob with the gray-role colour as its `var()` fallback.
  - PRD v0.8.11 also drops the §9.8 claim that the `.dark` / `.light` classes exist for shadow tokens that
    `light-dark()` cannot carry. Whether the classes exist stays with row `Z14`.
  - One `patch` changeset for `@websublime/line-tokens` (PROCESS §6, Phase 00 after `0.1.0`).

## Acceptance criteria
1. PRD v0.8.11 records the decision; §9.12 and §9.8 follow it. Spec `AM-054` (trigger `decision`) amends §6.C.2
   with the shadow contract and §6.F.4 with the new Playwright check. Both land in one `docs` commit before any
   code. A grep for `--line-gray-a-12` and for the old §9.8 shadow rationale returns zero live hits.
2. `shadows.css` declares no reference to an undeclared token, and every knob it declares is read.
3. A Playwright check (`packages/line-tokens/__tests__/shadows.e2e.ts`, chromium, firefox, webkit) loads the
   built `dist/` CSS. It fails on `main` and passes on the branch. It covers these cases:
   - Every `--line-shadow-*` token computes a `box-shadow` other than `none`.
   - In light, each layer's alpha equals `--line-shadow-strength` plus its offset. In a `color-scheme: dark`
     container on a light page, it equals `--line-shadow-strength-dark` plus the offset.
   - The colour equals the nearest gray role. This holds at the root, in a nested `[data-gray]`, and in a nested
     `[data-accent]` without `data-gray` (auto-pair).
   - Without `line-themes`, the colour equals `--line-neutral-*`.
   - Overrides of `--line-shadow-color`, `--line-shadow-strength` and `--line-shadow-strength-dark` on `<html>`
     reach a nested theming scope.
4. The `shadows.css` header comment and the `line-tokens` README state the colour dependency
   (`line-colors`, and `line-themes` for the gray tint) and where overrides apply.
5. A `patch` changeset for `@websublime/line-tokens`. Verify record green: `bun run lint`, `bun run build`,
   `bun run e2e`, `bun run scripts/lint-layers.mjs`.

## Public surface touched
- `--line-shadow-color`, `--line-shadow-strength`, `--line-shadow-1..6`, `--line-shadow-inner-1..3` change
  value. Today they compute `none` or invalid.
- New tokens: `--line-shadow-strength-dark` and the per-offset colour tokens (names fixed in AM-054).
- `shadows.css` declarations move from `:where(html)` to `:where(html, [data-accent], [data-gray])`. The knobs
  stay at `:where(html)` if the AM adopts that default.

## Spec drift found
- PRD §9.12 says every `line-tokens` declaration uses `:where(html)`. The chosen selector contradicts it.
- PRD §9.8 justifies the `.dark` / `.light` classes with shadow tokens that `light-dark()` cannot carry. After
  this row no shadow token needs them.
- `shadows.css` comment calls `--line-shadow-color` and `--line-shadow-strength` themeable. Overrides reach the
  shadow tokens only where those tokens are declared.
