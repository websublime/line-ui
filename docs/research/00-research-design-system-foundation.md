> **TL;DR — read this first.**
>
> The R11 stop gate (Bun test + `@open-wc/testing-helpers`) is **PARTIALLY CONFIRMED** — the helpers themselves are DOM-only and will load under Bun's `bun:test`, but their auto-cleanup side-effect silently no-ops (Mocha-style globals are not installed by Bun). This is **not** a hard incompatibility and does **not** force a return to plan + PRD revision; it requires an explicit `afterEach(fixtureCleanup)` wiring per test file or via a Bun preload. Recommendation: proceed to spec with that wiring as a documented constraint.
>
> However, **three other contradictions are larger than R11** and must be resolved before any spec work:
>
> 1. **`@zag-js/element` does not exist** (R3). The current Zag adapter for vanilla / custom elements is `@zag-js/vanilla` (exports `VanillaMachine`, `normalizeProps`, `spreadProps`, `mergeProps`). Plan, PRD, and ARCHITECTURE all reference a non-existent package name. Spec must rename the integration target.
> 2. **`@radix-ui/colors` does not ship `contrast` tokens nor per-hue CSS files** (R1). It ships TS modules of hex values (`light.ts`, `dark.ts`, `blackA.ts`, `whiteA.ts`) and exports them via a single `.` entrypoint. The 31-hue × 12-step structure holds, but everything CSS-shaped — `.css` files per hue, `light-dark()` wrappers, `--line-{hue}-contrast` tokens — must be **authored / generated by us**. The contrast table is a `radix-ui/themes` concept, not part of `@radix-ui/colors`.
> 3. **`rolldown-vite` is explicitly experimental** in Vite 7 (R5). Vite 7 ships with the legacy Rollup as default. Rolldown is opted into via an npm `overrides` swap (`"vite": "npm:rolldown-vite@latest"`). The plan/PRD assumption that "Vite 7+ with Rolldown" is a stable, single shipping target is wrong. Spec must either (a) treat Rolldown as a deliberate experimental opt-in with a documented rollback to Rollup, or (b) defer Rolldown to a later phase.
>
> Two more risks should be flagged for spec time:
>
> 4. **`ElementInternals` is not testable under happy-dom** (R8). The feature request is open (capricorn86/happy-dom#1419). jsdom has only partial coverage (`setFormValue` #3831 and `setValidity` #3758 are still open). The FormAssociated mixin's contract has to be verified in real browsers via Playwright — not in `bun test`.
> 5. **HTMX does not cross shadow DOM by default** (R15). Integration requires the host element to invoke `htmx.process(shadowRoot)` and `hx-*` attributes inside shadow DOM use the `host` / `global` selector escapes. The HTMX spike (Stream H) is feasible but the adapter has a more interesting surface than the plan's one-liner implies.
>
> **Recommendation:** Do not proceed straight to spec. Resolve C1 (Zag adapter rename), C2 (Radix CSS pipeline scope), C3 (Rolldown opt-in policy) by **plan + PRD revision** (per the project's no-silent-pivot rule, §5.2/R11). The remaining items can be carried as spec-level facts.

## Dependencies Investigated

### R1 — `@radix-ui/colors` (npm registry)

- **Latest version:** **3.0.0** (`dist-tags.latest`, npm registry).
- **Source shape (verified against `radix-ui/colors` main branch):**
  - Single TS package; entry point `./src/index.ts` re-exports `./dark`, `./light`, `./blackA`, `./whiteA`.
  - Light file exports **31 saturated/grayscale hues** matching the PRD list (amber, blue, bronze, brown, crimson, cyan, gold, grass, gray, green, indigo, iris, jade, lime, mauve, mint, olive, orange, pink, plum, purple, red, ruby, sage, sand, sky, slate, teal, tomato, violet, yellow). Confirmed by `grep -E '^export const [a-z]+ ='` over `light.ts` → 31 entries.
  - Dark file exports the same 31 hues with the `Dark` suffix (`indigoDark`, `redDark`, …).
  - Each hue exports an object with **12 numeric steps** (`indigo1` … `indigo12`) as hex strings — e.g. `indigoDark` from `src/dark.ts`:
    ```ts
    export const indigoDark = {
      indigo1: "#11131f", indigo2: "#141726", indigo3: "#182449",
      indigo4: "#1d2e62", indigo5: "#253974", indigo6: "#304384",
      indigo7: "#3a4f97", indigo8: "#435db1", indigo9: "#3e63dd",
      indigo10: "#5472e4", indigo11: "#9eb1ff", indigo12: "#d6e1ff"
    };
    ```
  - Alpha and P3 variants ship alongside (`indigoA`, `indigoP3`, `indigoDarkA`, `indigoDarkP3`).
- **Capabilities:** 31 hues × 12 steps × {light, dark, alpha, P3}. Hex strings only.
- **Limitations / contradictions vs plan:**
  - **No CSS files are shipped.** The published `exports` map in `package.json` is `{ ".": { import / require } }`. There is no `./amber` / `./blue` subpath. The per-hue `.css` files described in PRD §9.9 and plan §2.1 do **not** exist upstream — they must be generated by `line-colors` build scripts.
  - **No `light-dark()` shipping.** Light and dark are separate object exports. Wrapping both into `light-dark(...)` is a transformation we own.
  - **No `contrast` token.** Plan R1 asks to "validate the static contrast colour per hue". `@radix-ui/colors` (the palette package) ships **no contrast tokens at all**. Contrast tokens are a `@radix-ui/themes` (themes runtime) concept — they exist as `--{hue}-contrast` CSS variables in Radix Themes' compiled stylesheets, not in the colors package. The PRD §9.2 statement "12 steps + 1 `contrast` token per hue. Sourced from `@radix-ui/colors`" is **factually wrong as to the source**. The per-hue contrast table (PRD §9.2: "amber, yellow, lime, mint, sky, cyan → `#000`; rest → `#fff`") is correct as a design rule, but must be **authored by us**, not extracted from upstream.

### R2 — CSS `light-dark()` browser support

- **Source:** caniuse.com (`mdn-css_types_color_light-dark`).
- **Minimum versions:** Chrome 123, Firefox 120, Safari 17.5. Global usage ~87%.
- **`color-scheme` inheritance into Shadow DOM:** `color-scheme` is an inherited CSS property and does propagate into open shadow roots. Verified by MDN docs and standard practice; the PRD §9.8 claim "color-scheme inherits through Shadow DOM boundaries" is consistent with the spec.
- **Limitations:** No polyfill path is needed for the latest-2 matrix; older Safari (≤16) and older Chrome/Firefox would fall back to the first argument of `light-dark()` (an invalid value), so any consumer targeting <Safari 17.5 / Chrome 123 / Firefox 120 must either ship a sass/postcss expansion or accept light-mode-only on legacy.

### R3 — Zag.js framework-agnostic adapter

- **Latest version:** `@zag-js/core` v1.40.0, `@zag-js/dom-query` v1.40.0 (npm registry).
- **Available framework adapters** (from `chakra-ui/zag` main branch, `packages/frameworks/`): `preact`, `react`, `solid`, `svelte`, `vanilla`, `vue`. **There is no `element` adapter.** `https://registry.npmjs.org/@zag-js/element` returns `{"error":"Not found"}`.
- **The actual vanilla adapter:** `@zag-js/vanilla` v1.40.0. Inspecting its `src/index.ts`:
  ```ts
  export { mergeProps } from "./merge-props"
  export { normalizeProps } from "./normalize-props"
  export { spreadProps, type Attrs } from "./spread-props"
  export { VanillaMachine } from "./machine"
  ```
  The `VanillaMachine` class wraps the schema-driven machine model from `@zag-js/core` (imports `createScope`, `Machine`, `Service`, `bindable` etc.). `bindable` is also re-exported via the vanilla adapter.
- **Capabilities:** Framework-agnostic, returns a `Service<T>` you can subscribe to; lifecycle methods are `start()` / `stop()` (the `cleanups: VoidFunction[]` are flushed on stop). Compatible with any custom-element class — call `start()` in `connectedCallback`, `stop()` in `disconnectedCallback`.
- **Lit 3 compatibility:** No special adapter needed. Lit 3's `connectedCallback` / `disconnectedCallback` are the natural mounting/unmounting hooks. `VanillaMachine` is independent of Lit's reactive system; bridging is done by calling `requestUpdate()` on the Lit host from a `subscribe` callback.
- **Contradiction:** Plan §2.5, PRD §2/§9, and ARCHITECTURE §8 reference `@zag-js/element` by name. That package name does not exist. The correct integration target is `@zag-js/vanilla` (`VanillaMachine`, `bindable`, `normalizeProps`, `spreadProps`, `mergeProps`) plus direct consumption of `@zag-js/core` `createMachine`.

### R4 — Lit 3+ latest

- **Latest version:** `lit` v3.3.3 (npm registry).
- **`static formAssociated = true` pattern:** Lit `LitElement` extends `ReactiveElement` which extends `HTMLElement`. The `formAssociated` static is a **platform-level contract** (any class extending `HTMLElement` participates by declaring `static formAssociated = true` and calling `this.attachInternals()` in the constructor). Lit does not provide first-class sugar for this; it works because LitElement does not override the platform behavior. Common community pattern (verified across multiple Lit-based component libraries, e.g. `@shoelace-style/shoelace`, `@spectrum-web-components`):
  ```ts
  class MyControl extends LitElement {
    static formAssociated = true;
    #internals = this.attachInternals();
    // setFormValue / setValidity called from reactive callbacks
  }
  ```
- **`::part()` and `color-scheme` inheritance:** Standard Shadow DOM behaviour; nothing Lit-specific blocks the plan.
- **Status:** CONFIRMED. The plan's R4 assumption "Lit 3+ supports formAssociated + ElementInternals + ::part + color-scheme inheritance" holds. Caveat: the support is delegated to the platform, not added by Lit.

### R5 — Vite 7+ with Rolldown

- **Latest Vite:** v7.x stable.
- **Source:** v7.vite.dev/guide/rolldown.
- **Status of Rolldown integration:** **Explicitly experimental.** Quote: "rolldown-vite is explicitly experimental … breaking changes might be introduced even within its patch versions … rolldown-vite only receives updates for its most recent minor version."
- **How to opt in:** Via `package.json` `overrides` (or pnpm/Bun equivalents): `"overrides": { "vite": "npm:rolldown-vite@<pinned>" }`. The default `vite@7` install ships with Rollup.
- **Known caveats:** Option-validation warnings on Rollup-only options; `manualChunks` renamed to `advancedChunks`; some plugins requiring `transformWithEsbuild` need a separate `esbuild` install; library-mode is not explicitly covered in the v7 Rolldown guide (no documented caveats, but no documented guarantees either).
- **Contradiction with PRD/plan:** PRD §2 says "Bundler: Vite 7+ with Rolldown" as a single, decided technology choice; PRD §2.1 says "Vite 7 stabilises the Rolldown integration that was experimental in earlier versions". Per upstream documentation, this is **wrong**: Vite 7 itself stabilises, but the Rolldown integration is still experimental and is delivered through the separate `rolldown-vite` package via overrides, not through `vite@7` directly.

### R8 — `ElementInternals` API

- **Browser support (MDN):** "Baseline widely available", available across browsers since March 2023. `setFormValue`, `setValidity`, `reportValidity`, `checkValidity`, `:invalid` / `:valid` reflection are all standard and supported in latest-2 Chrome/Firefox/Safari.
- **Safari quirks:** Form-associated custom elements landed in Safari 16.4 (March 2023). Earlier Safari versions silently no-op. No known quirks in latest-2.
- **Test-environment support (critical caveat):**
  - **happy-dom — NOT supported.** Issue `capricorn86/happy-dom#1419` ("Add support for ElementInternals interface") is **open**, last updated 2025-02-18. No `attachInternals()` implementation.
  - **jsdom — partial.** `#3561` (basic `HTMLElement.attachInternals`) closed; `#3654` (basic ElementInternals) closed. But `#3831` (`setFormValue`) and `#3758` (`setValidity`) remain **open**.
- **Implication:** The FormAssociated mixin's behaviour (the actual `setFormValue` / `setValidity` lifecycle) **cannot** be verified in `bun test` + `@happy-dom/global-registrator` and only partially in `bun test` + jsdom. Verification has to run in real browsers via Playwright (R12). The plan acceptance criterion §7.3 — "FormAssociated mixin verified against a native `<form>`" — therefore implies a Playwright test, not a Bun unit test.

### R11 — `@open-wc/testing-helpers` + Bun test compatibility *(decision gate)*

- **Latest version:** `@open-wc/testing-helpers` v3.0.1 (npm registry).
- **Runtime dependencies:** `lit ^2 || ^3`, `lit-html ^2 || ^3`, `@open-wc/scoped-elements ^3.0.2`. **No `peerDependencies`. No dependency on `@web/test-runner`, no dependency on `mocha`, no dependency on `chai`.** The package is pure DOM utilities.
- **What the package actually does** (verified by reading source files at `open-wc/open-wc/packages/testing-helpers/src/`):
  - `fixture.js`: re-exports `fixture` / `fixtureSync`, then runs a side-effect that tries to register a Mocha-style `afterEach(fixtureCleanup)` if either `'afterEach' in window` or `'teardown' in window`. The whole side-effect is wrapped in `try { ... } catch { /* do nothing */ }`.
  - `fixtureWrapper.js`: stores wrapper nodes in a module-level `cachedWrappers` array, removes them with `document.body.removeChild` on cleanup. Pure DOM.
  - `elementUpdated.js`: awaits `el.updateComplete` (Lit) or `el.componentOnReady()` (Stencil), else `await nextFrame()`. Pure DOM + microtask.
  - `lib.js`: uses `Symbol.iterator`, `Node`, `isTemplateResult` from `lit/directive-helpers.js`. Pure DOM + Lit.
- **Bun test compatibility analysis:**
  - Bun's `bun:test` does **not** install Mocha-style globals on `window` (it exports `afterEach` / `beforeEach` etc. from `bun:test` only). `@happy-dom/global-registrator` registers DOM globals but does not patch `window.afterEach`.
  - Consequence: the `try { if ('afterEach' in window) afterEach(...) }` block in `fixture.js` falls through silently — the auto-cleanup **does not register**.
  - The `fixture()`, `fixtureSync()`, `html`, `elementUpdated()` core APIs **continue to work** because they are pure DOM and only need a globalThis `document`. happy-dom provides that.
  - To restore cleanup behaviour, a Bun preload script (per `bunfig.toml [test] preload`) can call `import { fixtureCleanup } from '@open-wc/testing-helpers/index-no-side-effects.js'; import { afterEach } from 'bun:test'; afterEach(fixtureCleanup);`. This is a one-liner wiring, not a fork.
- **Custom-element support under bun:test + happy-dom:** Bun's official docs (bun.sh/docs/test/dom) include a custom-element worked example that imports happy-dom and calls `customElements.define`. The PRD's "minimum testable unit" for the design system is **CSS snapshot tests** (plan §4.3 C9) — those don't need helpers at all. The runtime-core integration test (plan §7.3, "hello world component built using `LineElement`") is the first place `@open-wc/testing-helpers` would actually be used.
- **Verdict:** **PARTIALLY CONFIRMED — not a stop gate.**
  - Core fixture API works under `bun test` + `@happy-dom/global-registrator` because it only needs `document`.
  - Auto-cleanup silently no-ops. Workaround is one preload file.
  - Form-associated / ElementInternals behaviour is not exercisable here (R8) regardless of whether `@open-wc/testing-helpers` is used — that limitation is in happy-dom, not in the helpers.
- **Per §5.2/R11 of the plan, the decision gate fires only on "incompatibility".** The findings are not incompatibility, they are a **documented constraint with a one-line workaround**. The plan's R11 stop rule does not have to fire. However, the spec must document:
  1. That `@open-wc/testing-helpers` is loaded under `bun test` + happy-dom.
  2. The preload-registered `afterEach(fixtureCleanup)` wiring.
  3. That browser-level tests (FormAssociated, real `light-dark()` resolution, real custom-state) run in Playwright (R12), not in `bun test`.

### R15 — HTMX integration patterns

- **Latest HTMX:** v2.0.10 (`htmx.org` on npm).
- **Behaviour with Shadow DOM** (source: htmx.org/examples/web-components/): "HTMX doesn't know anything about your web components, and won't see anything inside their shadow DOM."
- **Required pattern:**
  1. The custom element must call `htmx.process(this.shadowRoot)` once in `connectedCallback` (or after the first render) so HTMX scans the shadow root.
  2. `hx-*` attributes inside the shadow root use the `host` selector to reference the host element and the `global:` selector to escape into the document.
  3. The custom element must re-process on any swap that mutates shadow-DOM subtree it owns; HTMX's `htmx:afterSettle` event drives the swap-aware lifecycle.
- **Feasibility for `LineHtmxElement`:** The adapter is a thin mixin that (a) calls `htmx.process(this.shadowRoot)` in `connectedCallback`, (b) listens for `htmx:beforeSwap` / `htmx:afterSettle` on `this`, (c) forwards `hx-*` attributes from the host into the shadow root or vice-versa depending on direction. This is **feasible**, not pre-cravado. Plan §2.8's "spike must complete; outcome documented as committed or exploratory" remains the correct framing.
- **Risk:** HTMX 2 plus shadow DOM is a community pattern, not a first-party feature. Documentation is thin. The spike should produce a small worked example (one form-style component + one HTMX endpoint) before the committed/exploratory decision is recorded.

### R16 — Icon libraries (reference choice for registry validation)

- **Lucide** v1.16.0 (npm `lucide`). 1500+ icons, MIT, individual SVG modules, treeshakeable per-icon imports.
- **Phosphor Icons** `@phosphor-icons/core` v2.1.1 (npm). Six weights (thin/light/regular/bold/fill/duotone) — interesting surface area for the registry, but more bundle weight per icon.
- **Iconoir** v7.11.0 (npm). 1700+ icons, MIT, similar shape to Lucide.
- **Recommendation:** **Lucide** as the Phase 00 reference. Lightest per-icon footprint, simplest module shape (one SVG export per icon, no weight axis), broadest community familiarity. Phosphor's weight axis is more interesting for the registry's "resolver API" design but adds noise to the Phase 00 validation.
- **Registry-contract implications:** Any of the three exposes a `{ default: SVGElement | string }` per-icon module; the registry API can normalise to `(name) => Promise<SVGTemplateResult | Element | string>`. All three are compatible with the agnostic-resolver contract from PRD §6.2 / ARCHITECTURE §11.

## Contradictions and Risks

### C1 — `@zag-js/element` adapter does not exist *(blocking)*

- **Plan / PRD / ARCHITECTURE say:** Plan §2.5, §4.4/D6, §5.1/R3 reference "`@zag-js/element` adapter" as the Zag.js binding for vanilla custom elements. ARCHITECTURE §6 introduction notes "Zag.js lifecycle now explicitly stated to integrate via the `@zag-js/element` adapter". ARCHITECTURE §8 and §13 reference the same name.
- **Reality:** No `@zag-js/element` package is published on npm (registry returns `{"error":"Not found"}`). The Zag.js monorepo (`chakra-ui/zag`, `packages/frameworks/`) ships these adapters: `preact`, `react`, `solid`, `svelte`, `vanilla`, `vue`. The correct adapter for vanilla / web components is **`@zag-js/vanilla`**, exporting `VanillaMachine`, `normalizeProps`, `spreadProps`, `mergeProps` (and re-exporting `bindable` from `@zag-js/core`).
- **Impact:** Every reference to `@zag-js/element` in plan / PRD / ARCHITECTURE is a dangling pointer. Implementation cannot proceed against a non-existent package.
- **Recommendation:** Plan + PRD + ARCHITECTURE must be revised to replace `@zag-js/element` with `@zag-js/vanilla`. The integration semantics (call `start()` in `connectedCallback`, `stop()` in `disconnectedCallback`, machine teardown via the returned cleanup array) are unchanged — only the package name is wrong.

### C2 — `@radix-ui/colors` does not ship CSS or contrast tokens *(blocking for design-system spec scoping)*

- **Plan / PRD say:** PRD §9.2: "12 steps + 1 `contrast` token per hue. Sourced from `@radix-ui/colors`". PRD §9.7: "Build script reads `@radix-ui/colors`, emits `line-colors/src/{hue}.css`". Plan §4.3/C3: "palette generation script — reads `@radix-ui/colors`, emits one CSS file per hue with 12 steps in `light-dark()` + static `contrast` token".
- **Reality:**
  1. `@radix-ui/colors` ships TS hex-string objects only. No CSS, no subpath exports.
  2. Light and dark hues are separate exports (`indigo`, `indigoDark`). No `light-dark()` wrapping upstream.
  3. **There is no `contrast` token of any kind in `@radix-ui/colors`.** The contrast concept lives in `@radix-ui/themes` (the React component library), where it is emitted as `--{hue}-contrast` in the compiled themes stylesheet using a hand-authored per-hue colour rule (white text for most hues, black text for `amber, yellow, lime, mint, sky, cyan`).
- **Impact:** The plan's framing — "read upstream, emit CSS" — undersells the work. The `line-colors` build pipeline must:
  1. Author the per-hue contrast table (white vs black step-9 foreground) ourselves.
  2. Pair light and dark hue objects into `light-dark()` declarations.
  3. Choose whether to emit alpha (`*A`) and P3 (`*P3`) variants now or in a later phase (the PRD §9.2 mentions only the base 12-step + contrast — alpha/P3 are not in scope).
  4. WCAG-validate each contrast choice (plan §4.3/C4) — the validation cannot defer to upstream because the choices are ours.
- **Recommendation:** Spec should explicitly state that `@radix-ui/colors` is the **value source** (hex strings) and that `line-colors` owns the entire CSS transform: pairing, `light-dark()` wrapping, per-hue contrast authoring, and WCAG validation. PRD §9.2 and §9.7 wording must be revised to reflect this scope.

### C3 — Vite 7's Rolldown integration is experimental, not stable *(blocking unless explicitly scoped)*

- **Plan / PRD say:** PRD §2: "Bundler: Vite 7+ with Rolldown". PRD §2.1: "Vite 7 stabilises the Rolldown integration that was experimental in earlier versions". Plan §5.1/R5 phrasing matches.
- **Reality:** Vite 7 ships with Rollup as default. Rolldown is a separate package (`rolldown-vite`) that is opted into via `package.json` `overrides` aliasing. Upstream calls it **"explicitly experimental"** and warns that "breaking changes might be introduced even within its patch versions". Library-mode behaviour is not specifically called out as stable.
- **Impact:** Choosing Rolldown for Phase 00 is a deliberate experimental decision, not a stable default. It is acceptable to make that choice, but the plan / PRD must not present it as a finalised stable stack. If Rolldown breaks library-mode CSS pipelines (which is the heart of the design-system build per plan §4.3/C8 + §7.2), the fallback is to drop the override and use Rollup — and that must be a documented rollback path.
- **Recommendation:** One of:
  - **Option A (proceed):** Spec explicitly opts into `rolldown-vite` via overrides, pins the version, documents the experimental status, and includes a "rollback to Rollup" runbook. Risk register entry §8 of the plan ("Vite 7 + Rolldown instability on library-mode CSS — Medium / High — fall back to Vite 7 with Rollup") becomes the canonical operating mode.
  - **Option B (defer):** Phase 00 uses Vite 7 + Rollup. Rolldown adoption is a Phase 1 follow-up. PRD §2 and §2.1 are revised accordingly.

### R1 — happy-dom does not implement `ElementInternals`

- **Risk:** Plan §7.3 acceptance criterion "FormAssociated mixin verified against a native `<form>`" cannot be satisfied by `bun test` + `@happy-dom/global-registrator`. happy-dom #1419 is open; jsdom is only partial (#3831 and #3758 still open for `setFormValue` and `setValidity`).
- **Evidence:** Searched both repos' open issue trackers; verified upstream issue states.
- **Mitigation options:**
  - Make Playwright the canonical environment for the FormAssociated integration test (one browser-level test that submits a `<form>` containing a `<line-input>` and asserts the request payload). This aligns with R12 already being in the stack.
  - Add a unit-level test that **mocks** `attachInternals` under happy-dom (verifies the mixin calls `setFormValue` / `setValidity` with the right arguments) and pair it with the Playwright browser-level submission test.
- **Recommendation:** Update plan §7.3 acceptance to: "FormAssociated mixin's argument contract verified under `bun test` (via mocked `attachInternals`); native `<form>` participation verified end-to-end via one Playwright test in CI."

### R2 — `@open-wc/testing-helpers` auto-cleanup silently no-ops under Bun

- **Risk:** The `fixture.js` side-effect registers `afterEach(fixtureCleanup)` only if `'afterEach' in window`. Bun's `bun:test` exports `afterEach` from the module, not as a global. happy-dom's `GlobalRegistrator.register()` does not install test-framework globals. Result: fixture nodes accumulate in `document.body` across tests.
- **Evidence:** Source inspection of `open-wc/open-wc/packages/testing-helpers/src/fixture.js` and `fixtureWrapper.js`; Bun docs (bun.sh/docs/test/dom and /test/writing).
- **Mitigation:** A two-line Bun preload registers the cleanup explicitly:
  ```ts
  // bun-test-preload.ts
  import { GlobalRegistrator } from "@happy-dom/global-registrator";
  GlobalRegistrator.register();
  import { afterEach } from "bun:test";
  import { fixtureCleanup } from "@open-wc/testing-helpers/index-no-side-effects.js";
  afterEach(fixtureCleanup);
  ```
  Referenced from `bunfig.toml`:
  ```toml
  [test]
  preload = ["./bun-test-preload.ts"]
  ```
- **Recommendation:** Spec must include this preload as a project-standard testing fixture and reference it from the `Getting Started` / contributor docs.

### R3 — Storybook version drift (plan says 8, latest is 10)

- **Risk:** Spec written against Storybook 8 would target a deprecated major. Storybook 9 introduced breaking changes to addons; Storybook 10 finalised them.
- **Evidence:** `storybook` v10.4.0 latest on npm; `@storybook/web-components-vite` v10.4.0 with `peerDependencies.storybook: "^10.4.0"`.
- **Mitigation:** Target Storybook 10 in the spec. CEM analyser integration is unchanged.
- **Recommendation:** Minor PRD/plan revision: replace "Storybook 8" with "Storybook 10 (latest)" in plan §2.4, §4.6/F1, and PRD §5.1.

### R4 — HTMX + Shadow DOM requires explicit wiring

- **Risk:** Plan §2.8 / §4.8 / §7.8 frames the HTMX spike as adapter feasibility. The actual integration requires per-component `htmx.process(this.shadowRoot)` calls, the `host` / `global` selector escapes for `hx-target`, and swap-aware re-processing on `htmx:afterSettle`. The "feasible/risks" judgement therefore has more surface than the spike currently implies.
- **Evidence:** htmx.org/examples/web-components/.
- **Mitigation:** Spike should produce a concrete worked example (one form-shaped component + one server endpoint round-trip + one shadow-DOM swap), not just an API sketch.
- **Recommendation:** Acceptance criterion §7.8 stays as written ("outcome documented; committed or exploratory"), but the spike's deliverable must include a runnable example, not only prose.

## Open Questions

1. **Radix Colors variant scope.** PRD §9.2 mentions only the 12-step base palette + contrast. The npm package also ships alpha (`*A`) and Display-P3 (`*P3`) per hue. Are alpha and P3 in scope for Phase 00, Phase 1, or deferred? *Needs product decision.*
2. **Rolldown opt-in policy.** Should Phase 00 adopt `rolldown-vite` deliberately (with documented experimental status + rollback) or defer to Rollup until Vite ships Rolldown as default? See C3 Options A and B. *Needs architect + maintainer decision.*
3. **Storybook 8 vs 10 target.** Drop-in version bump or worth a full survey of breaking changes? *Recommend: target latest (Storybook 10) and accept the version bump.*
4. **Per-hue contrast WCAG threshold.** WCAG AA is the plan acceptance threshold (§4.3/C10). The Radix Themes convention is white text on most hues; bright hues (`amber, yellow, lime, mint, sky, cyan`) get black. Should we adopt this table verbatim, or run our own per-hue AA/AAA computation and tune from the result? *Needs design decision; affects C2.*
5. **Reference icon library for Phase 00.** Recommendation is Lucide for simplicity. Is the team comfortable picking Lucide, or do we want to validate the registry contract against two libraries (e.g. Lucide + Phosphor) to surface design pressure on the resolver API? *Needs product / DX decision.*
6. **FormAssociated test stratification.** Plan §7.3 requires "verified against a native `<form>`". Confirm acceptance language to require: (a) `bun test` unit-level mocked verification of the mixin's contract, AND (b) one Playwright browser-level form-submission test in CI. *Needs architect + QA decision.*
