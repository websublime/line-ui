## Part A — Requirements

### Overview

#### Description

`<line-kbd>` shows a keyboard shortcut drawn for the user's device (PRD §4.1, `docs/PRD.md:260`). The author writes the shortcut once in the `keys` attribute, such as `keys="mod+k"`, and the component draws `⌘K` on Apple devices and `Ctrl+K` elsewhere (P2; F2, F3). `mod` stands for the main modifier, Command on Apple devices and Control elsewhere (F2). Keys pressed together join with `+`, and keys pressed one after another are separated by a space, such as `keys="g i"` (F6). Assistive technology reads words for the glyphs, such as "Command K", in place and inside the name of a control around it (P3; F4). The words are English by default, and the consumer replaces them (F5). The component reads the platform from the browser and takes a `platform` attribute that overrides it (P1; F1). When `keys` yields no key, it shows its own content as written. It only displays the shortcut; the app handles the keys. It has no events and takes no focus.

#### Use cases

- A shortcut hint in a command palette trigger, such as "Search ⌘K" (P3).
- The shortcut beside a menu item, such as "Copy ⌘C", whose menu item carries `aria-keyshortcuts` (P3; F7).
- A key sequence in a help panel, such as "G then I" for "go to issues" (P3; F6).
- A key named in prose, such as "Press Esc to close" (P2).
- A shortcut an agent shows in generated UI, through the `keys` prop (P9).

#### Anti-patterns

- Handling the shortcut. Kbd registers no key handler; the app binds the keys (D7).
- Showing a shortcut the app does not handle in the current context. The hint then promises an action that never runs.
- Naming the host with `aria-label`. The host has no role, so the label names a `generic`, which ARIA prohibits (R8 `:55`; P3, P4).
- Displaying source code or program output. Use `<code>` or `<samp>`.
- Declaring the shortcut to assistive technology. That belongs on the owning control as `aria-keyshortcuts` (R8 `:77`; F7).

#### User expectations

- The shortcut looks the way the user's own system shows it, with `⌘` glyphs on a Mac and `Ctrl+` words on Windows and Linux (P2; F3).
- A screen reader reads the keys as words, such as "Command K" or "Ctrl Shift P", not as symbol names (P3, P5; F4).
- A sequence reads as steps, "G then I" (P3; F6).
- The hint is not a button and does not take focus (D7).

## Part B — Technical Specification

### Anatomy

```
<line-kbd>                              LineElement; :host display: inline-flex (D3)
└── #shadow-root
    └── <kbd part="root">               inline-flex; gap --line-kbd-gap (D5)
        ├── <kbd part="item">           one key; a glyph key holds
        │   ├── <span aria-hidden="true">⌘</span>     the glyph
        │   └── <span class="word">Command</span>      the visually hidden word (F4)
        ├── <span part="separator" aria-hidden="true">+</span>   between the keys of a chord, off Apple only (F3)
        ├── <kbd part="item">K</kbd>    a word key holds its visible word
        ├── <span class="word"> then </span>          between the steps of a sequence (F6)
        └── <kbd part="item" data-step>I</kbd>         the first key of each later step
    while parsing keys yields no key:
    └── <kbd part="root"><slot></slot></kbd>
```

- The outer `<kbd>` represents the whole input and each inner `<kbd>` one key, as the HTML Standard nests them for a key combination ("the `kbd` element", `html.spec.whatwg.org/multipage/text-level-semantics.html#the-kbd-element`). `<kbd>` adds no role and no node to the Chromium tree (P3; R8 `:77`).
- `root` is the ARCH §5 name for the main container, `item` for each item of a list, and `separator` for a separator (`docs/ARCHITECTURE.md:306`, `:317`, `:316`; F8 (a)).
- `.word` carries the Visually Hidden recipe that `0012-visually-hidden.md` F5 (d) settled, `position: absolute` with logical insets, a 1 px box, `overflow: hidden`, `clip-path: inset(50%)` and `white-space: nowrap`. The stylesheet repeats it, because MANIFESTO Law 4 forbids importing `<line-visually-hidden>` (D17).
- `data-step` is an internal attribute that the stylesheet keys the sequence gap on (D5).
- `willUpdate` parses `keys` and resolves the platform into a private field, and `render` maps the result to the template, so render holds no parsing (MANIFESTO Law 5, `docs/MANIFESTO.md:47`; D8).

#### Keys grammar (F2, F6)

- `keys` holds steps separated by whitespace, and a step holds keys joined with `+`. Leading, trailing and repeated whitespace and empty keys are dropped (D9).
- The component renders the default slot when parsing yields no key, as for an absent attribute, a blank value or a value of separators only, such as `keys="+"`. Otherwise it draws the keys and does not render the slot (F2 (c); D9).
- Key names are case-insensitive. The table lists every name with a platform-specific drawing; any other name draws its own text, a single character upper-cased and a longer name with its first letter upper-cased, such as `K`, `?`, `F5` or `Insert` (P2).
- The `+` key is written `plus` and the space bar `space`, because `+` and whitespace are the separators, as in GitHub's hotkey syntax (`github/hotkey`; Primer `KeybindingHint` `props.ts`, read 2026-11-13).
- Each key resolves to a word id, the last column of the drawing table; an unknown name's id is the name lower-cased and serves dedupe only. Its text is never looked up in `key-labels` or `LineKbd.keyLabels`, so `keys="then"` draws "Then", and `{"k": "X"}` changes nothing. Within a step, a repeated word id draws once, at its first occurrence, so `shift+mod+alt+ctrl+k` draws `Shift+Ctrl+Alt+K` off Apple, where `mod` and `ctrl` both resolve to `control` (D9).

#### Drawing table (F3, F4, F5)

| Name, with aliases | Apple: glyph, then hidden word | Other: visible word | Word id |
|---|---|---|---|
| `mod` | `⌘`, "Command" | "Ctrl" | as `meta` on Apple, as `control` elsewhere |
| `meta` (`cmd`, `command`) | `⌘`, "Command" | "Meta" | `meta` |
| `control` (`ctrl`) | `⌃`, "Control" | "Ctrl" | `control` |
| `alt` (`option`, `opt`) | `⌥`, "Option" | "Alt" | `alt` |
| `shift` | `⇧`, "Shift" | "Shift" | `shift` |
| `enter` (`return`) | `↩`, "Return" | "Enter" | `enter` |
| `escape` (`esc`) | `⎋`, "Escape" | "Esc" | `escape` |
| `backspace` | `⌫`, "Delete" | "Backspace" | `backspace` |
| `delete` (`del`) | `⌦`, "Forward Delete" | "Del" | `delete` |
| `tab` | `⇥`, "Tab" | "Tab" | `tab` |
| `space` | "Space", no glyph | "Space" | `space` |
| `up` (`arrowup`), `down` (`arrowdown`), `left` (`arrowleft`), `right` (`arrowright`) | `↑`, "Up Arrow"; `↓`, "Down Arrow"; `←`, "Left Arrow"; `→`, "Right Arrow" | the same glyphs with the same hidden words | `up`, `down`, `left`, `right` |
| `pageup`, `pagedown`, `home`, `end` | "Page Up", "Page Down", "Home", "End", no glyph | the same words | `pageup` … |
| `plus` | `+`, "Plus" | "Plus" | `plus` |
| between steps | the hidden word "then" | the same | `then` |

- The modifier ids are `control`, `alt`, `shift` and `meta`. On Apple, the modifiers of a step draw first, sorted Control, Option, Shift, Command, as Apple's guidelines require ("List modifier keys in the correct order", `developer.apple.com/design/human-interface-guidelines/keyboards`, read 2026-11-13), and every other key follows in the author's order, with no separator. So `k+mod` draws `⌘K`, `mod+k+j` draws `⌘KJ`, and a step of modifiers only draws them sorted (P2; F3 (a)).
- Off Apple, keys keep the author's order and join with a `separator` part holding `+` (P2; F3 (a)). The words "Ctrl", "Alt", "Shift", "Esc", "Del", "Backspace" and "Tab" are the Microsoft Writing Style Guide key names (`learn.microsoft.com/en-us/style-guide/a-z-word-list-term-collections/term-collections/keys-keyboard-shortcuts`, read 2026-11-13). "Page Up", "Page Down", "Home" and "End" take the same title case on both platforms, where the Microsoft guide writes "Page up" in sentence case.
- Off Apple, the `plus` key draws the word "Plus", because a `+` key beside the `+` separator reads as `Ctrl++` (P2). The Microsoft guide spells this key out as a word, "Plus sign", and Kbd uses the shorter "Plus" that Primer's `full` format draws (`primer/react` `packages/react/src/KeybindingHint/key-names.ts`, `fullKeyName`, read 2026-11-13; D21).
- The Apple words are Apple's key names, as the same guidelines list them ("Control, Option, Shift, and Command"); "Return", "Delete" and "Forward Delete" name the keys Apple keyboards print [INFERENCE: the keycap names are not in the cited page].
- Arrow keys draw as arrows on every platform, because keyboards label them only with an arrow (Microsoft guide, "arrow keys"), and carry hidden words, because a glyph alone reaches the name as a glyph (P3).
- The word id keys the F5 override. `mod` takes the id of the key it resolves to.
- The hidden span between steps holds the `then` word with one space on each side, as the probe drew it (P3), so an override `"then": "dann"` renders " dann ".

#### Words and their override (F5 (d))

- The English words above are defaults. The consumer replaces any of them through the app-wide static `LineKbd.keyLabels` and the per-host `key-labels` attribute, which holds a JSON object as a string.
- Both take a flat map from an id to a word. An id is a word id, such as `"control"` or `"then"`, or a platform-qualified id, `apple.<id>` or `other.<id>`, such as `"other.control"`, so `{ "other.control": "Strg", "apple.alt": "Wahltaste", "then": "dann" }` localises German drawings.
- For each word the component takes the first entry that exists, in this order:
  1. the attribute's platform-qualified id;
  2. the attribute's bare id;
  3. the static's platform-qualified id;
  4. the static's bare id;
  5. the English default.
- The two maps merge per id, so an attribute that sets only `then` keeps the static's other words. With `key-labels='{"control": "X"}'` and `LineKbd.keyLabels = { "other.control": "Strg" }`, an `other` host draws "X".
- A `key-labels` value that is not a JSON object whose values are all strings is ignored as a whole, so the lookup falls through to the static and the defaults, and the component throws nothing (MANIFESTO Law 9; D9).
- `willUpdate` reads the static on each update, so a page sets it before its hosts render, and a host already rendered picks up a changed static on its next update (D8).

### F1 — Platform detection and override

**Evidence.** In probe P1, `navigator.platform` reads `MacIntel` on this host in all three engines, under every Playwright user-agent option and device preset; only a Chromium CDP override changes it. Chromium exposes `navigator.userAgentData` only in a secure context, and there Playwright's Windows user-agent string makes `userAgentData.platform` read "Windows" while `navigator.platform` reads `MacIntel`. Firefox and WebKit have no `userAgentData`. Zag reads `userAgentData.platform` first, then `navigator.platform`, and matches `/^Mac/i` (`@zag-js/dom-query` 1.47.0 `dist/platform.mjs:5-8`, `:33`). Primer's `KeybindingHint` groups macOS and iOS as `apple`, separates `windows` only to name the Meta key "Win", defaults to `other` when `navigator` is undefined, and offers a context override "primarily intended for testing and Storybook" (`primer/react` `packages/react/src/KeybindingHint/platform.ts`, `main`, read 2026-11-13). In probe P8, Bun and Node both define `navigator`, with `platform` `MacIntel` on this host, and happy-dom reports `X11; Darwin arm64`. MANIFESTO puts SSR out of scope for v1 (`docs/MANIFESTO.md:65`).

| Option | What it decides | Consequence |
|---|---|---|
| (a) **Recommended.** UA-CH, then `navigator.platform`; a `platform` attribute | `auto` reads `navigator.userAgentData?.platform`, else `navigator.platform`, and calls `/^(Mac\|iPhone\|iPad\|iPod)/i` Apple; `platform="auto \| apple \| other"`, default `auto`; no `navigator` → `other` | Works where UA-CH is missing (insecure Chromium contexts, Firefox, WebKit) and prefers the newer source where it exists (P1). Tests, stories and docs pages force a drawing in every engine (P1, P2). iPadOS and iOS hardware keyboards draw `⌘` [INFERENCE: device behaviour not observed] |
| (b) As (a), no attribute | detection only | One less prop. Tests and visual baselines cannot pin a drawing, because Playwright cannot change `navigator.platform` (P1) |
| (c) `navigator.platform` only, with the attribute | ignores UA-CH | One source. `navigator.platform` is the older API and may be frozen or reduced by browsers [INFERENCE: no browser announcement checked] |
| (d) User-agent string, with the attribute | parses `navigator.userAgent` | The repo's chromium and firefox projects send a Windows string from a Mac (P1), so tests would draw Windows while `navigator.platform` says Mac |
| (e) As (a) with three values, `apple \| windows \| other` | Windows is detected separately | `meta` can draw "Win" on Windows, as Primer does. One more value to test and document; apps rarely bind the Windows key [INFERENCE] |

The value names `apple` and `other` follow Primer and cover iPhone and iPad. `mac` reads more familiarly and would mislabel an iPad.

### F2 — Authoring API

**Evidence.** PRD §4.1 asks for "OS-aware rendering (Cmd vs Ctrl)" (`docs/PRD.md:260`), and the Phase 1 spec C14 row repeats it (`:1170`). Slotted text cannot change per platform without the component rewriting light DOM, which MANIFESTO Law 5 forbids (`docs/MANIFESTO.md:47`). In probe P9, a `keys` string through a `DynamicString` prop and an attribute binding renders, updates on a bound value, and degrades to an empty host. In probe P7, a host with only `keys` shows nothing before the upgrade, and slotted text shows. In probe P6, swapped hosts and swapped slot content render under htmx 2 and 4. Primer's `keys` prop takes the same chord and sequence syntax (`props.ts`).

| Option | What it decides | Consequence |
|---|---|---|
| (a) `keys` only | the component draws from `keys`; no slot | One input. Nothing shows before the upgrade (P7); a key the grammar lacks can only draw as written |
| (b) Slotted `<kbd>` content only | the consumer writes the drawing | No OS awareness, so the PRD row is not met |
| (c) **Recommended.** `keys`, with the default slot as fallback | `keys` draws when it holds a key; otherwise the slot shows as written | OS-aware drawing for markup and agents (P9). Fallback text shows before the upgrade (P7; D20) and covers keys outside the grammar. Two content paths, documented as one rule |
| (d) Named slots per platform | the consumer writes `<span slot="apple">` and default content; the component picks one | No parsing and no English words. Every author writes both drawings and their spoken words; an agent would need two props, and the text binding writes only the default slot (Phase 1 spec §6.G.1, `:1312`) |

### F3 — Drawing per platform

**Evidence.** Apple lists the modifier symbols and requires the order Control, Option, Shift, Command (`developer.apple.com/design/human-interface-guidelines/keyboards`, read 2026-11-13). The Microsoft Writing Style Guide names "Ctrl", "Alt", "Shift", "Esc", "Del", joins keys with `+`, and writes both "Alt+Ctrl+S" and "Ctrl+Shift+?" in its own examples, so it fixes no modifier order (keys and keyboard shortcuts term collection, read 2026-11-13). Primer draws glyphs on every platform in its default `condensed` format, `⌃` for Control off Apple included, and words joined with `+` in `full` (`key-names.ts`, `Chord.tsx`). Probe P2 shows drawing (a); probe P5 shows that a hidden `+` needs a flex root to keep the words apart. PRD §4.1 writes "(Cmd vs Ctrl)" (`docs/PRD.md:260`).

| Option | What it decides | Consequence |
|---|---|---|
| (a) **Recommended.** Apple glyphs, words elsewhere | On Apple, the glyphs of the drawing table, with no separator, in Apple's modifier order. Elsewhere, keycap words joined by an `aria-hidden` `+`, in the author's order. Letters upper-case on both | Each platform reads as its own system shows shortcuts (P2). Reads PRD's "(Cmd vs Ctrl)" as the Command-versus-Control distinction, not as the literal text "Cmd" |
| (b) As (a), with a fixed order off Apple | off Apple, the order Ctrl, Alt, Shift, Meta, then the key | One drawing per chord off Apple. Microsoft's own examples use two orders, so the fixed order has no source |
| (c) Glyphs everywhere | `⌃` for Control off Apple, as Primer's `condensed` | Compact. Windows and Linux keyboards print "Ctrl", not `⌃` [INFERENCE: keycaps not surveyed] |
| (d) Words everywhere | "Cmd+K" on Apple, "Ctrl+K" elsewhere | Matches the PRD text literally. Apple's own menus and guidelines use glyphs, so a Mac user reads an unfamiliar form |
| (e) A `format` attribute | `glyphs \| words`, as Primer's `condensed \| full` | Both drawings on demand. One more prop, and the default still needs (a) or (d) |

Option (d) is the only one that needs no reading of the PRD row. Miguel chose (a) and reads PRD §4.1 "(Cmd vs Ctrl)" as the Command-versus-Control distinction, so the PRD row needs no revision (2026-11-13).

### F4 — Accessible text of glyphs

**Evidence.** In probe P3, glyphs as text reach a button's name as glyphs, "Search ⌘K". NVDA's English table names `⌘` and `⌥` and not `⇧` or `⌃`, and CLDR's English speech names call `⇧` "upwards hollow arrow" (sources in P3). A hidden glyph beside a visually hidden word gives "Search Command K" in all three engines, and the hidden span keeps the word apart from the next key. A host `aria-label` names a `generic`, which ARIA prohibits (R8 `:55`), and axe does not report it on a custom element (P4). An internals or inner `img` gives an `image` node named "Command K". MANIFESTO puts component-level strings out of scope (`docs/MANIFESTO.md:66`), which F5 settles. Primer renders each key as a visually hidden word plus an `aria-hidden` glyph (`Key.tsx`).

| Option | What it decides | Consequence |
|---|---|---|
| (a) **Recommended.** Hidden glyphs, hidden words | each glyph is `aria-hidden`; a visually hidden word sits beside it in the shadow tree; words off Apple are visible text; the root is `inline-flex` | "Command K" and "Ctrl Shift P" in three engines (P3, P5). The words are strings, so F5 decides where they come from |
| (b) Glyphs as text | no words | No strings. What a screen reader says depends on its symbol table, and NVDA has names for `⌘` and `⌥` only, while CLDR calls `⇧` "upwards hollow arrow" (P3) |
| (c) Host `aria-label` from a label prop | the consumer writes "Command K" | Names a prohibited `generic` (R8 `:55`); axe does not catch it (P4); the consumer must know the platform to write the label |
| (d) Internals `img` with a host `aria-label` | Badge's named-count pattern (`0007-badge.md` F5) | A valid name on an `image` node (P3); the consumer still writes a platform-specific label |
| (e) A label prop rendered as hidden text | the consumer's words replace the glyphs for assistive technology | No built-in strings; the consumer must know the platform to write the label |

### F5 — Words and localisation

**Evidence.** MANIFESTO Out of Scope says "Labels like "Close", "Dismiss", "Loading" are the consumer's responsibility via slots and attributes. No bundled i18n." (`docs/MANIFESTO.md:66`). R8 lists strings that "must come from the consumer through slots or attributes" (`:286-287`). Phase 1 spec AM-013 records Miguel's choice of "consumer-settable live-region attributes with English defaults over attributes with no default and over a MANIFESTO reading that keeps fixed English strings" (`:2474`), and ARCH §17.4 states that the consumer localises those strings (`docs/ARCHITECTURE.md:1643`). Off-Apple key words differ by keyboard locale, such as "Strg" for Ctrl on German keyboards [INFERENCE: keycaps not surveyed]. In probe P9, the surface writes only descriptor bindings, so a per-host attribute outside the descriptor never reaches an agent-rendered host. ARCH §17.2 C1 lists string, number, boolean, string enum and the two array types (`docs/ARCHITECTURE.md:1572`).

| Option | What it decides | Consequence |
|---|---|---|
| (a) English only | the drawing table's words, no override | Simplest. Departs from MANIFESTO Out of Scope, so it needs a MANIFESTO or PRD decision |
| (b) English defaults, `key-labels` attribute | a per-host JSON object of word overrides | Follows the AM-013 reading. Agent-rendered hosts keep English unless the descriptor exposes `keyLabels` to agents |
| (c) English defaults, static `LineKbd.keyLabels` | one app-wide map | Reaches every host, agent-rendered ones included. A page with two languages cannot vary the words per section. The static is outside C1's element inputs (Agent contract) |
| (d) **Recommended.** (b) and (c) | the attribute wins over the static, the static over the defaults; ids may be platform-qualified (Part B) | Every host can be localised, agent-rendered ones through the static, and one section can differ through the attribute. Two inputs to document |
| (e) No defaults | the consumer must supply every word; without words, glyphs are text, as F4 (b) | No bundled strings. Most consumers ship glyphs that screen readers name inconsistently (P3) |

Option (d), which Miguel chose, needs no higher-document revision under the AM-013 reading of MANIFESTO Out of Scope. It records `LineKbd.keyLabels` under the C1 exclusions, as the template asks.

### F6 — Sequences

**Evidence.** In probe P3, two keys with no word between them read "Search GI", and a visually hidden " then " reads "Search G then I" in three engines. In probe P2, the steps draw as `GI` without a gap. Primer and GitHub's hotkey syntax separate steps with a space and render a hidden "then" (`Sequence.tsx`). The Microsoft guide distinguishes a key combination from a key sequence.

| Option | What it decides | Consequence |
|---|---|---|
| (a) **Recommended.** Space-separated steps | `keys="g i"`; each later step starts with a `--line-kbd-sequence-gap` margin and a hidden " then " word (an F5 id) | Reads as steps (P3). `space` names the space bar, because a space separates steps |
| (b) Chords only | one step per host; a space is an error or ignored | No hidden "then". GitHub-style shortcuts need two hosts and the consumer's own word |
| (c) A visible separator | "then" or `→` drawn between steps | Sighted users see the order. A visible word is one more string; `→` collides with the right-arrow key |
| (d) A separate attribute | `sequence` holds steps, `keys` one chord | Two inputs for one idea; the agent needs two props |

### F7 — `aria-keyshortcuts`

**Evidence.** R8 says "The control that owns a shortcut can state it with `aria-keyshortcuts`" (`:77`). In probe P3, Chromium exposes it as the `keyshortcuts` property of a button and a menu item. ARIA takes modifier names `Alt`, `Control`, `Shift`, `Meta` and `AltGraph` and `KeyboardEvent.key` values (WAI-ARIA 1.2, `aria-keyshortcuts`). The value must describe the binding the app handles, which the app decides. Every `Element` already has an `ariaKeyShortcuts` property that reflects `aria-keyshortcuts` on that element (ARIA reflection, ARIAMixin) [INFERENCE: not probed on the host].

| Option | What it decides | Consequence |
|---|---|---|
| (a) **Recommended.** Documentation only | the docs and JSDoc tell the owning control to carry `aria-keyshortcuts` with the app's binding | No API. The value matches what the app binds, even when a docs page forces `platform` |
| (b) A read-only property | for example `shortcut`, returning `"Meta+K"` or `"Control+K"` for the resolved platform; not `ariaKeyShortcuts`, which reflects on the Kbd host itself | Keeps the value in step with the drawing. Reports the forced platform on a docs page; one more public member; additive later |
| (c) A `for` attribute | Kbd writes `aria-keyshortcuts` on the element whose id it names | Writes another element's attribute, which MANIFESTO Law 4's slot-and-orchestrator wiring and Law 5's DOM rule leave to the consumer (`docs/MANIFESTO.md:45`, `:47`) |
